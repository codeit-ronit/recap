# W4 evaluation datasets: provenance

M6 W4 evaluates RECAP's components separately, each on its own data. This folder holds that
data. Nothing in it is ever read by RECAP's retriever, memory, router, prompts or agents: only
the scorers in `evals/` read it (checked by `tests/unit/test_w4_leakage.py`).

| file | what it is | how it was made | edited by hand? |
|---|---|---|---|
| `retrieval-v1.yaml` | 31 runbook queries and what counts as relevant to each | generated by `python -m evals.datasets` from the scenarios, the runbooks and the paraphrase file | no (a test checks it is current) |
| `retrieval-paraphrases-v1.yaml` | 12 hand-written queries, each labelled with a failure mechanism | written by the evaluator on 2026-11-08, before any retrieval result for them existed | yes, and never after a result was seen |
| `labels-v1.yaml` | per scenario: partition, alerted and root service, mechanism, exact fix, cross-service or not; every (scored scenario, train scenario) memory pair labelled | generated by `python -m evals.datasets` from the scenarios' evaluation-only `expected` blocks | no (a test checks it is current) |
| `query-vectors-v1.json` | nomic-embed-text vectors of the 27 distinct query texts above (they include every query the W4 split's hybrid runs search with) | captured on 2026-11-08 with the local Ollama embedder (`python -m evals.components --capture-query-vectors`), 27 embedding requests | no |

## Retrieval queries (`retrieval-v1.yaml`)

- **alert** (17): every scenario's alert as RECAP's controller writes its first runbook query:
  the alerted service and the alert's symptoms, joined (`IncidentController._retrieve`).
  `tests/integration/test_eval_runner_w4.py` checks that this is exactly what the runs searched.
  Each carries its scenario's partition (train 3, test 8, demo 6), and scores are also kept per
  partition in the component report.
- **proposal** (2): the controller's remediation lookup for each mechanism that has a
  recommended action (`IncidentController._maybe_retrieve_runbook`).
- **paraphrase** (12): `retrieval-paraphrases-v1.yaml`, verbatim.

**Relevance.** A chunk is relevant to a query about mechanism M when its document declares M
(a `Mechanism: M` line), and is a *remediation* chunk when it holds a `Recommended action:`
for M. These lines are the runbooks' own: nothing was labelled by hand. The cascading-failures
guide declares `dependency_failure` but deliberately recommends no action for it (a dependency
failure is a symptom), so `dependency_failure` has relevant chunks and no remediation chunk.
`unknown` has neither and is not scored.

**Answers.** Each alert query's mechanism comes from its scenario's `expected` block, which no
agent ever sees. The dataset is derived from it for scoring only.

**Caveats.** Relevance is document-level (a chunk of the right runbook counts, whichever
section). The paraphrases were written by someone who had read the runbooks: they test
wording that differs from the corpus, on a small N, and are not an independent test set.

## Labels (`labels-v1.yaml`)

- `fix` is the scenario's fix as a proposal states it. For a rollback, the target is the
  root service's previous deployment before the bad release (from the scenario's own
  deployment history), e.g. `execute_rollback on cart (to_version=v2.1.0)`.
- `cross_service`: the root cause sits behind the alerted service.
- `memory_pairs`: every scored (test-partition) scenario with every train scenario:
  - `twin`: the remembered fix is exactly today's fix (reuse would be right);
  - `same_diagnosis`: same service and mechanism, another fix (e.g. a rollback to another
    version: reuse would be wrong);
  - `look_alike`: another service or mechanism (reuse would be wrong).

The memory component judges each memory hit of a batch's runs against these labels: a hit
judged safe whose label is not `twin` is unsafe reuse.

## Query vectors (`query-vectors-v1.json`)

Format `recap-vectors-v1` (the runbook vectors' format, `recap/knowledge/vectors.py`), keyed by
a hash of exactly what was embedded (`search_query: ` + the query). The file also lists every
query text it holds (`queries`). It records the model (`nomic-embed-text`, 768 dimensions),
the query prefix, the Ollama version (0.34.4) and the weights digest
(`sha256:970aa74c…`), which equals the stored runbook vectors' digest: hybrid search refuses
query and runbook vectors made from different weights.

An evaluation answers every hybrid query from this file and refuses a query it lacks, so a
changed query is never approximated: capture again instead (needs Ollama with
nomic-embed-text, briefly; `OLLAMA_NO_CLOUD=1 ollama serve`, loopback only).

## Leakage rules these datasets follow

- No scenario answer reaches RECAP: the answers are read by `evals/` scorers only, and no
  module under `recap/` reads this folder or names a scenario outside docstrings and comments.
- The runbooks carry no scenario id and no scenario's bad release version.
- Train, test and held-out scenarios stay apart (`evals/splits/w4.yaml`, labels checked).
- No SREGym problem is part of any W4 dataset or split: SREGym's held-out problems are W5's.
