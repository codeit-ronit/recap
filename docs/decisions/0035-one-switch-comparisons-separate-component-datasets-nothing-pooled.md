# ADR 0035: One switch per comparison, a dataset per component, and nothing pooled across kinds of evidence

**In one sentence:** RECAP's AI architecture is evaluated by pairs of configurations that differ
in exactly one switch (checked before any run, and again from the runs' own records), by
component evaluations that each use their own dataset (retrieval, memory, routing, budgets,
verifier, safety), and by records that carry every switch they ran with; no number is ever
pooled across configurations, components or evaluation modes.

## Status

Accepted (M6, W4; built 2026-11-08). Extends [ADR 0029](0029-one-evaluation-record-per-run-and-modes-that-never-share-a-number.md)
(one record per run, modes that never share a number) and relies on [ADR 0023](0023-memory-partitions-by-origin-and-evidence-checked-reuse.md)'s
memory partitions. The work and its results are logged in [m6-progress.md](../m6-progress.md);
how to run and read it is in [evaluation.md](../evaluation.md) section 13.

## Context

M4's scripted benchmark compared configurations, but its baseline differed from the full
system in three switches at once, its configurations' runs were never paired, its records did
not say which budget, context limits, memory partitions or router rules a run used, and the
components themselves (retrieval, memory verdicts, routing decisions) were never measured on
their own. Hybrid retrieval needed a live embedding model, so no evaluation measured it. The
real-model batches hold one run per configuration, and the local model cannot run when the
laptop is short of memory.

W4's question is what each existing component contributes, without inventing improvements or
rates, and without tuning on the scenarios used to measure.

## Decision

1. **Records say everything that could explain a difference.** `EvalRecord` gains defaulted
   fields: seed, fixture hash, router, verifier, policy version, safety switch, planner,
   memory partitions read and written, the effective budget and context limits, the budget
   stop, router rules per round, agents, decisions, evidence per agent and the evidence the
   supported claims rest on per agent, disagreements, claims by verifier status, mechanism
   correctness, unsafe actions (attempted, blocked, executed, refused), injection flags,
   context items dropped and shortened, each proposal's source, the writes carried out and
   those aimed off the root-cause service. Older batches load unchanged: a missing value reads
   "not recorded", never zero.
2. **A comparison changes one switch, checked twice.** A comparison names two configurations
   and the switch between them (`evals/comparisons/*.yaml`). Before anything runs, the runner
   refuses a pair whose effective RunConfigs differ in anything else. After the runs,
   `evals/compare.py` pairs them by scenario and seed and lists any recorded provenance that
   differs beyond the switch (prompt version, code version, budgets, memory partitions...).
   Paired outcomes ("only the variant recovered s2"), not two rates, are the result.
3. **A held-out set is only measured.** A split may name `held_out` scenarios: scored with the
   test suite, never looked at to choose a change. W4's two are held out from W4's choices
   only; earlier milestones developed and regression-test RECAP on them, and the docs say so. Configurations cannot set what the runner
   owns (provider, recording, approvals, label, latency), and the evaluation always runs on
   the simulator, whatever `RECAP_TARGET` says.
4. **Each component has its own dataset, derived, not hand-labelled where avoidable.**
   Retrieval relevance comes from the runbooks' own `Mechanism:` and `Recommended action:`
   lines; alert queries are exactly the controller's first query; twelve hand-written
   paraphrases are kept in their own file with their provenance. Memory pairs are labelled
   twin, same diagnosis or look-alike by comparing each scenario's exact fix (a rollback's
   target included) with the remembered one. All of it is generated by `evals/datasets.py`,
   committed, and checked current by a test; RECAP's own code never reads it.
5. **Hybrid retrieval is measured offline.** The evaluation's queries are deterministic, so
   they are embedded once with the local model and stored (`evals/datasets/query-vectors-v1.json`,
   the runbook vectors' format, weights digest included). A run answers from the file and
   refuses a query it lacks; a capture refuses a server with other weights.
6. **Component results have their own report, never a success rate.** `evals/components.py`
   writes a `recap-component-report-v1` (retrieval scores per ranker and query kind, memory
   verdicts, routing, budget, verifier and safety rows) next to, not inside, the batches; the
   API serves it at `GET /evals/components`, and the Evaluations page shows it in its own
   section, one disclosure per component.
7. **A real-model pilot is prepared, not run, until it can run safely.** `evals/plans/w4-pilot.yaml`
   states its runs, budget and the decision each result would change; RECAP's memory guard
   decides whether it may start.

## Consequences

### Good

- A difference between two configurations can be traced to its switch, and a confound shows
  up as a flagged difference instead of a silent one.
- Retrieval, memory and routing each have numbers of their own, including the dense-only
  ranker and the poisoned-runbook exposure that end-to-end runs could not show.
- Hybrid search is reproducible offline and in CI, with no model server.

### Bad

- More fields per record, and the comparison table is only as good as the configurations'
  one-switch discipline (enforced, but a new switch needs a mapping in `evals/compare.py`).
- The stored query vectors must be captured again whenever a query changes (a scenario's
  alert, the remediation lookup's wording); until then hybrid evaluations refuse to run.
- The scripted policy makes every decision in these batches: they measure RECAP's code
  paths, not a model's use of them. The datasets are small and partly written by the
  evaluator.

## Alternatives considered

- **Rates per configuration with confidence intervals.** Rejected: eight scenarios per
  configuration support counts and paired outcomes, not rates.
- **A second evaluation framework.** Rejected: the existing runner, records, categorizer and
  batches were extended instead; one record format serves every mode.
- **Embedding queries live during the evaluation.** Rejected: it would make the measurement
  depend on a running model server, and a re-pulled model could change it unseen.
- **Hand-labelled relevance judgments.** Mostly avoided: the runbooks already state which
  mechanism and action each section covers; only the paraphrases are hand-written.
